# Commit & Push Policy

This policy is designed to be simple and readable for both humans and automated agents.
It defines a small set of symbols to describe the nature of each commit, plus a few basic workflow rules.


## 1. Commit Types (Symbols)

Each commit should clearly indicate what kind of change it contains.
Use one or more of the following symbols in the **commit message title**:

- `add = {+}`   → You **added** something new (files, functions, tests, docs).
- `del = {-}`   → You **deleted** something (files, code, unused functions).
- `mod = {~}`   → You **modified/improved** existing code or docs.
  - There was **no actual bug**, you just enhanced, refactored, or cleaned up.
- `fix = {#}`   → You **fixed a problem**.
  - There was a bug, wrong behavior, or error, and you corrected it.
- `major = {!}` → **Important change** / big advancement.
  - New feature, big refactor, or something that teammates **must pull** soon.
- `docs = {...}` → **Documentation-only change**.
  - README updates, comments, guides, policies; no behavior change in code.
- `tests = {%}` → **Tests-only change**.
  - New unit tests, functional tests, or adjustments to existing tests.

You can combine them if needed, for example:

- `{+}` `add: new linked list utility`  
- `{~}` `mod: improve Makefile logs`  
- `{#}` `fix: handle NULL in my_strdup`  
- `{!}{#}` `major fix: new memory model for allocator`  
- `{...}` `docs: add README section for libmy usage`  
- `{%}` `tests: add unit tests for my_strcpy`  
- `{%}{#}` `tests fix: update failing list tests after bugfix`  

Keep the text after the symbols short and descriptive.


## 2. What to Commit

Commit only meaningful, intentional changes:

- Source code: `*.c`, `*.h`, and other real project sources.
- Build and tooling files: `Makefile`, scripts, configs.
- Tests: test sources and stable test data.
- Documentation: `README.md`, `COMMIT_POLICY.md`, etc.


## 3. What NOT to Commit

Never commit generated or temporary files:

- Object files: `*.o`.
- Binaries and executables: no compiled programs or temporary test binaries.
- Rebuildable libraries: `libmy.a`, `*.so`, `*.dylib`.
- Coverage outputs: `*.gcda`, `*.gcno`, reports like `coverage.html`, `*.css`.
- Logs: `*.log`.
- Editor/OS junk: swap files, backup files, `.DS_Store`, etc.

If it can be regenerated by `make` or another command, it should **not** be versioned.


## 4. Basic Workflow Rules

These are the simple rules everyone (including agents) must follow:

- Do **not** push something that is **not finished**.
- Do **not** push without having **pulled** the latest changes.
- Do **not** push without having **tested** your code.

Before committing or pushing:

1. **Update your branch**
   - Use **merge by default**: `git pull`.
   - Use `git pull --rebase` **only in case of emergency** (for example, to clean up a broken local history), and only if you understand the impact.

2. **Build**
   - Root project: `make`.
   - Library only: `make -C lib/my`.

3. **Run tests** (if they exist)
   - `make tests_run`.

4. **Check your diff**
   - Make sure there are no generated files or junk staged.

The main branch should always be in a **buildable and stable** state.


## 5. Behavior for Automated Agents

Automated tools or agents must follow the same rules:

- Use the symbols `{+}`, `{-}`, `{~}`, `{#}`, `{!}`, `{...}`, `{%}` in commit titles.
- Never stage or commit generated artifacts (object files, archives, coverage, logs).
- Group logically related changes into a single commit.
- Run the relevant build and tests before committing, unless the explicit task is to show a failing state.

Example commit messages for agents:

- `{+} add: new malloc helper for file reading`
- `{~} mod: simplify coverage target in Makefile`
- `{#} fix: avoid segfault on empty list in get_front`
- `{!}{+} major add: full printf refactor with new specifiers`
- `{...} docs: create COMMIT_POLICY for team and agent`
- `{%} tests: add coverage tests for my_str_to_word_array`


## 6. Collaboration

- Keep commits small and focused so teammates can review them easily.
- Resolve merge conflicts carefully and re-run `make` (and tests) afterwards.
- If the workflow changes, update this file so humans and agents stay in sync.
